# 多智能体协作、身份署名与双轨版本控制纪律

同一知识库由人类与不同智能体协同维护。系统保持厂商中立，依靠真实署名溯源、系统轨与内容轨物理分离、人类手工修改保护及受控快照恢复维持协作秩序。

## 1. 厂商中立与真实身份署名

- 规范与技能仅定义「智能体」角色，不绑定特定宿主专有指令。
- 九类知识生产链文档（`manifest`、`artifact`、`library`、`atomic`、`moc`、`workbench`、`slice`、`toc`、`slice_toc`）统一采用 `created_by`（创建者）、`updated_by`（最近实质改写者）、`reviewed_by`（审核归属：`ai` 或 `human`）署名三元组。
- 智能体必须使用运行时真实自报身份署名，严禁冒用人类身份或将自动流程伪造为 `reviewed_by: human`。自报身份与 Git 作者仅作溯源记录，不替代人类审批凭据。

## 2. 系统轨与内容轨双轨版本隔离

系统代码维护与知识库内容演进分属两条独立版本轨迹，严禁混入同一提交：

1. **系统管理轨（`SYS` 轨）**：
   - 管辖 `GewuAtlas/` 程序目录（`AGENTS.md`、`rules/`、`skills/`、`scripts/`、`dicts/`、`references/`、`tests/`）；
   - 遵循「立项锁定起点与写范围 → 在途禁止零散微提交 → 实测通过后原子交付并结单」闭环。
2. **知识内容轨（`DOC` 轨）**：
   - 每个知识库在受保护运行态维护独立的专属内容 Git 仓库（自动忽略 `00-DropZone/`、`99-Assets/98-Archives/`、工作台 `source/` 与 `.trash/`）；
   - 单次操作预计改动或同一 `DOC` 工单累计改写超过 `20` 个文件时，运行态自动在修改前执行 `pre` 快照提交、修改后执行 `post` 提交；
   - 人类明确发出「提交 / 保存 / commit」指令且经体检无断链时，聚合提交当前内容变更。

## 3. 人类手工修改与删除保护（状态 4 与状态 2 协同）

人类直接在本地文件管理器或 Obsidian 中新增、修改、移动或删除库内文件（含 `10-Index/*.base` 看板与各域 `README.md`）属于正常最高优先级行为：

- **看板与导览防覆盖**：看板与导览同步默认跳过已存在文件，保护人类手写筛选器与说明，非显式授权严禁强制覆盖。
- **状态 4（人类删改且零断链）**：当检测到未提交的人类手工增删改且全库无悬空断链时，通过 `human-sync` 模式确认人类变更入库并保持版本树干净，运行时同步剔除已由人类删除文件的失效句柄。
- **状态 2（人类删除引发悬空断链）**：当人类删除卡片导致其他笔记出现悬空引用时，提交门禁自动阻断并触发 `GUARD: INPUT_REQUIRED`。智能体**严禁擅自恢复被人类删除的文件**，必须转而对引用方卡片清理或降级断链后再收口。

## 4. 可逆撤回（`undo`）与冲突熔断

- 知识库内一切删、写、覆盖、搬迁在改盘前均捕获受保护前置快照，改盘后生成行级 Diff 明细（`90-System/92-Logs/Changes/<YYYY-MM>/`）并分配 `chg_XX` 句柄。
- 仅当快照在保留期内、完整可验证且目标文件当前版本与操作后版本一致时，才允许执行撤回；撤回新建项同样软删入 `.trash/`，不执行物理硬删。
- 若目标文件在操作后又被人类手工编辑或删除（触发 `human_manually_edited` / `human_manually_deleted`），撤回操作强制熔断拦截（`E_UNDO_CONFLICT`），保留人类现场。

## 5. 30 天保留清理与日记永久豁免

- `.trash/` 回收站条目、普通变更前置快照与 `90-System/92-Logs/Changes/` 历史明细默认按 `30` 天保留窗口定期清扫；处于未决恢复核验状态的课题快照受保护，不按普通过期项清除。
- **历史保留铁律**：`05-Journal/`（含按月归档的 `YYYY/MM/` 日记）遵循「只归档不删除」原则永久留存，全生命周期严禁进入回收站、严禁被 30 天清理扫除或由 `undo` 销毁。
